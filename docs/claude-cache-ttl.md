# Claude 缓存 TTL 与 Plugin 接入

Helper 对接 CPA-Helper Plugin 的单请求 TTL 策略，并继续使用 CPA 原 usage 队列提供的 token 数量。Plugin 的执行元数据只说明该次请求采用的策略，不提供第二份 token 或金额账本。

## 启用顺序

1. 备份 Helper 数据库、CPA 完整配置及 Plugin 的 policy/state。
2. 使用包含本次接入的 Helper 构建。Plugin 0.1.9、0.1.10 的已知管理组合为 CPA v8.0.45；0.1.9 没有 TTL 能力。旧 Plugin 0.1.8 / CPA v8.0.32 的目录兼容保留。
3. 按 [Plugin v0.1.10 部署说明](https://github.com/xialss/CPA-Helper-Plugin/blob/v0.1.10/docs/claude-uniform-ttl.md) 安装对应 Plugin，并配置其明确要求的 payload、实际配置文件绝对路径和一致的调度方式，重启/重载校验。不要覆盖已有业务 payload 来强行通过校验；Helper 不自动修改 CPA 配置。
4. 在 Helper 中确认版本兼容、TTL 能力及配置状态，再进入自身 API Key 的策略编辑器，选择“继承 CPA”“5m”或“1h”。旧 Key 默认继承 CPA。
5. 保存后检查读回结果，并通过一次有缓存创建 token 的请求检查请求明细中的 TTL、来源和关联状态。配置已校验不代表已验证真实 provider 接受 TTL。

Plugin 的固定文件校验对完整配置文件生效；任何内容变化都可能使 guard 失效。应按 Plugin 文档重新校验，而不是仅保存 Helper Key 设置。Helper 的管理密钥始终留在后端。

## 三种 Key 设置

| 设置 | 含义 |
| --- | --- |
| 继承 CPA | 不强制覆盖请求的 TTL，恢复 CPA 原行为 |
| 5m | Plugin 使该次受控 Claude 请求的既有缓存断点统一使用 5m |
| 1h | Plugin 使该次受控 Claude 请求的既有缓存断点统一使用 1h |

Key 策略优先于冲突的输入 TTL，但不创建或移动缓存断点。非 Claude 和 count_tokens 不应用这一归属。清除选择会实际清除 Plugin 中的 Key TTL，不只是隐藏表单值。配置不可用时不能把保存成功解释为已生效。

响应模型核验已在 Plugin 0.1.10 移除，Helper 按能力隐藏相应管理入口并停止相关请求。请求记录已有的上游响应模型展示和审计保留，二者含义不同。

## 请求明细与费用

- **上游事实**：CPA usage 已提供可信 5m、1h 或合法 mixed 时优先使用。mixed 按上游两桶分别计价，不压成一个 TTL。
- **请求策略归属**：原 usage 只有 aggregate 时，Helper 可以使用同实例、同 execution、同 Key 的有效 Plugin 元数据，将该 aggregate 归属到一个 TTL。来源显示为 `enforced_request`，不能理解为上游实际 TTL 或缓存命中证明。
- **未取得归属**：显示 unknown 和原因，沿用既有 legacy 缓存写计价语义，不根据当前 Key 设置补历史。unknown 不表示确认使用了 5m。
- **无缓存创建**：TTL 为空，不因存在策略或元数据而制造缓存 token。

Claude 模型只配置 5m、1h 两档缓存写价格。1h 价格未配置时相应请求为未定价；显式填 0 表示免费。其他模型仍使用一档缓存写价格。

队列和 Plugin 元数据异步到达。Helper 先持久保存待办，再批量关联；短暂 missing 或 metadata 服务错误会在最多 5 分钟的本地等待窗口内补查。等待归属的请求尚未进入已完成费用和余额扣款，余额更新会相应延迟。系统设置中的“TTL 归属或入账处理中”数量还包括恢复入账或完成标记的待办，因此不能认为整个计数都尚未扣费。进程重启后待办可继续。

五分钟窗口针对 TTL 关联。所需价格信息不可用时，尚需首次计费的请求继续等待可靠定价，并显示采集错误；已处理扣款、仅等待完成收据的请求仍可恢复。价格加载失败也不应让本地 TTL 等待无限延长。

到达明确终态后，Helper 按已确定的依据首次入账。重复队列或恢复重试不会重复扣款。终态后迟到的元数据不会自动改变已采用的 TTL 或重扣历史余额；价格表的既有重算与历史流水规则继续适用。Plugin 元数据保留 24 小时，不承诺在保留窗口外重建事实。

CPA 队列的消费接口会直接移除消息，没有确认/重入队协议。Helper 会在 inbox 保存失败时暂停继续消费并重试当前批次；但如果进程恰在 CPA 出队后、SQLite 提交前退出，仍无法通过该接口保证恢复这批消息。已成功持久化的待办才具备本地重启恢复保证。

## 升级、停用与回滚

停用 TTL 前停止新增受控流量，并先处理或记录 Helper 中的 pending。清除 Key TTL 后，再按 Plugin 说明恢复 payload/routing 并重启 CPA。停用后仍可查询 Plugin 留存的旧执行事实，不能将当前停用状态当作过去未使用策略。

Helper 新库保留执行来源、脱敏前的安全来源身份和首次入账依据。开始新采集、产生待办或入账收据后，数据库迁移会拒绝可能丢失这些证据的回退；此时需恢复一致的升级前数据库备份，不允许静默删除证据并按旧语义重算。使用备份恢复时需同时考虑已入账流水和已消费队列，避免把同一批用量再次采集/扣费。

自动化验证使用临时 SQLite 和模拟 CPA/Plugin；真实 provider 账单、VPS 与生产配置仍需在实际部署中单独核验。
